Blocker presentation library

One row shape shared across every blocker surface. Two worked examples. One compact variant. One handoff-gap treatment.

sprint 057 · phase D.1 · §7 of the design spec · philosophy §3.9 (alarms are ranked and rare)

A blocker is a product fact — a state the record actually holds. Not a warning the caller can dismiss. Every blocker in every downstream artboard uses this shape.

Six required fields

rule id
Registered id from contracts/receiving-rules.yaml or contracts/run-close-rules.yaml. Monospace. Never paraphrased.
description
The rule's description string. Verbatim from the registry. Never rewritten for "friendliness".
affected record
Alias and current state of the record the blocker holds. Cites contracts/state-machines.yaml state names verbatim.
next actor
The caller_type that resolves. Names the authorization rule that grants the resolution.
current-caller action
What the reading caller may do now: view detail, request paperwork, request a re-check, redirect. Never a false control.
clearing operation
The registered operation that would clear the block, if any. Names the transition.

certificate_of_conformance_unverified
A certificate of conformance covering the delivered goods exists, but nobody has accepted it as evidence. Capturing records that paperwork arrived; it does not record that anyone read it.

Worked example · run-close-rule blocker

failed_measurement_has_quality_path
Every failed Measurement has a linked Nonconformance and required verification is complete. Resolution requires the required nonconformance, containment, disposition, rework, and verification records. This is the rule that blocks the first VF-003 close attempt.

Handoff-gap variant · driver returned an unregistered id

If the driver returns a blocker id the registry does not know, the surface renders a GrammarGap. The runtime creates it at the emit site via NormalizeMachineEvidence or CreateGrammarGap. The UI shows the raw id, the caller who saw it, and the gap record so the vocabulary bump can happen later.

What a blocker never carries

no dismiss
A blocker is a product fact. There is no "OK" or "Got it" that removes it. It clears when the state clears.
no snooze
Alarms are ranked and rare (philosophy §3.9). Deferral is not a UI action; it is a scheduling decision, and that decision lives in the run planning surface.
no generic copy
Never "an error occurred" or "this action isn't available right now". The rule id and the description carry the specific meaning.
no false controls
A resolve button appears only when the current caller can invoke the clearing operation. Otherwise the strip names the next actor and leaves the resolve out.
