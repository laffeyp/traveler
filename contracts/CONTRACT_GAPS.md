# Contract gaps and registry decisions — first slice (contracts-0.4.1)

*Typed log of every place the contract stack underspecified or conflicted, and how the registry extraction resolved it. Per the executor rule: a resolution is either a recorded registry decision (faithful to the higher-authority document) or a typed `ContractGap` for the Architect. Nothing here is invented behavior. Authority order: Contract Spec v0.4.1 > Harness v0.1.2 > VF-003 v0.1.1 > Build Readiness v0.2 > earlier docs.*

## Resolved as registry decisions (ratified for sprint 001)

### B-Q-1 — QualityContainmentAction state machine
**Tension:** Build Readiness §7.5 gives `QualityContainmentAction` a `required → active` lifecycle; Contract Spec §8/§10 first-slice state-machine lists omit it, while the handler-wrapper rule forbids transitions not in a registered machine.
**Decision:** registered a `QualityContainmentAction` state machine in `state-machines.yaml` (`null → required` via `StartQualityContainment`; `required → active` via `ActivateQualityContainment`). Additive, faithful to both docs. Type: registry decision (additive alignment item for the TAD amendment ledger).

### B-Q-2 — StartQualityContainment / ActivateQualityContainment from disposition_pending
**Tension:** Contract Spec §10.3 authorizes `StartQualityContainment` only as `Nonconformance: open → containment_required`. VF-003 calls `DefineAffectedPopulation` first (NC → `disposition_pending`) then `StartQualityContainment` then `ActivateQualityContainment`, and asserts NC == `disposition_pending` after step 028.
**Decision:** added explicit `disposition_pending → disposition_pending` self-loop transitions for both `StartQualityContainment` (emits `QUALITY_CONTAINMENT_REQUIRED`) and `ActivateQualityContainment` (emits `QUALITY_CONTAINMENT_STARTED`) in the Nonconformance machine. These emit the containment events without changing NC state, faithfully encoding Build Readiness §7.5's "when not already disposition_pending" conditional. The containment lifecycle itself is carried by the `QualityContainmentAction` machine (B-Q-1). Type: registry decision. *Highest-risk item — the handler must take the self-loop path, not force `open → containment_required`.*

### B-Q-3 — ReworkRun / Verification canonical names
**Tension:** Contract Spec §15 + TAD §5.8 use `ReworkRun` / `Verification`; Build Readiness §5.2/§7.5/§9.3 use `ReworkRecord` / `VerificationRecord`.
**Decision:** canonical = `ReworkRun`, `Verification` (higher authority wins). `records.yaml`, projections, and reports use the canonical names; Build Readiness's names are aliases, not carried forward. Type: registry decision.
**Alias map (for anyone reading Build Readiness §5.2/§9.3):** `ReworkRecord` -> `ReworkRun`; `VerificationRecord` -> `Verification`. `SerialHistory.source_records` and `RunCloseReport.source_records` use the canonical names and resolve cleanly against `records.yaml` (validator-confirmed: no dangling reference). Build Readiness §5.2/§9.3 should be corrected to the canonical names in a future amendment; the registry does not adopt the divergent spelling. Verified clean by the 6-critic adversarial pass (sprint 001); this was the single non-blocking finding and is resolved here.

### B-Q-4 — INVENTORY_IN_WIP cardinality
**Tension:** `StartRunWithInventory` moves both valve body and gasket to `in_wip`; VF-003 §10 lists `INVENTORY_IN_WIP` once.
**Decision:** `StartRunWithInventory` emits **one `INVENTORY_IN_WIP` per item moved** (two in VF-003). VF-003 §10's sequence is a non-exhaustive "highlights" list (its own header), so the Event Trace Tester asserts presence/order of highlighted events, not exact multiplicity. The InventoryItem state paths (valve_body ends `in_wip`, gasket passes through `in_wip`) are the binding assertions. Type: registry decision. Architect confirmed one-event-per-item.

### B-Q-5 — REDLINE_APPROVED cross-module producer
**Tension:** `RecordApprovalDecision` (Approval Module) drives `Redline: under_review → approved` and emits `REDLINE_APPROVED` (Redline Module); TAD §5.22 says events are emitted by the module owning the state change.
**Decision:** `events.yaml` registers `REDLINE_APPROVED` (and `REDLINE_REJECTED`) with `owning_module: redline` and `producer_operations: [RecordApprovalDecision]`. Producer ≠ owner is permitted and already occurs elsewhere in Contract Spec §13. The Redline machine lists `RecordApprovalDecision` as the `via` for the `under_review → approved`/`rejected` transitions. Type: registry decision.

### B-Q-6 — eleven registries
**Tension:** the abbreviated bootstrap summary listed nine registries.
**Decision:** added `observability-profiles.yaml` and `compatibility-profiles.yaml` (Contract Spec §3, §5). Every operation carries `observability_ref` + `compatibility_ref`. Type: inclusion, no behavior decision.

### B-Q-7 — BUILD_CHECK_FAILED vs BUILD_CHECK_BLOCKED (discovered during extraction)
**Tension:** TAD §5.12 names `BUILD_CHECK_FAILED` (+ `BUILD_BLOCKER_CREATED`); Build Readiness §7.3 says `RunBuildCheck` emits `BUILD_CHECK_PASSED or BUILD_CHECK_BLOCKED`. VF-003 only exercises `BUILD_CHECK_STARTED` + `BUILD_CHECK_PASSED`, so the failed/blocked path is non-VF-003.
**Decision:** canonical = `BUILD_CHECK_FAILED` + `BUILD_BLOCKER_CREATED` (TAD outranks Build Readiness). `BUILD_CHECK_BLOCKED` is not registered. Type: registry decision; flagged for Architect awareness.

## Scope decisions (registry boundary)

### Single source of truth for ownership
`modules.yaml` is the module **identity** registry; ownership of each record/operation/event is recorded on that record/operation/event (`owning_module`). This satisfies "exactly one owning module" by construction and avoids double-maintenance dangling. Faithful to TAD §5's intent.

### Events without a first-slice producer are deferred
The CI gate "no event without producer operation" means only events produced by a first-slice operation (§21.1) are registered. Deferred events with no first-slice producer (and thus excluded from `events.yaml` for now):
`INVENTORY_MOVED`, `INVENTORY_STATE_CHANGED` (no `MoveInventory` in first slice);
`AS_BUILT_PROJECTION_UPDATED`, `AS_BUILT_PROJECTION_REBUILT` (projection-worker producers, not first-slice);
`MRB_DECISION_RECORDED`, `CAPA_STUB_CREATED`, `FOD_INCIDENT_OPENED/CLOSED` (Quality ops not in §21.1);
`EVIDENCE_ACCEPTANCE_POLICY_CREATED`, `EFFECTIVITY_AMBIGUITY_RESOLVED`, `SUPPORT_ACCESS_*`, `SERVICE_ACCOUNT_*`,
all Reconciliation / Adapter Runtime / Virtual Factory Harness / Human Validation / GrammarGap-lifecycle events.
These are registered when their producer operations enter a later slice. Type: scope note, not a gap.

### Measurement is result-valued, not a state machine
Per Contract Spec §11, `Measurement.result ∈ {not_evaluated, pass, fail, warning}`; no Measurement state machine is registered. VF-003 §1.3's "required state machines" wording is superseded by §11. `scenario-assertions` target `Measurement.result`. Type: registry decision.

### RunStep creation is implicit
Per Contract Spec §0.2.7, `RunStep` is created under `CreateRun` with no own creation event; its machine declares `creation_transition: implicit_under_CreateRun` and has no `null ->` row. The four records mandated explicit creation transitions (Run, InventoryItem, MachineEvidenceRecord, Nonconformance, plus QualityContainmentAction) each have a `null ->` row (Contract Spec §0.1.4). Type: registry decision.

## Discovered during sprint 002 (schema-generation review)

### B-Q-8 — Operation output shape: Build Readiness §4.3 vs Harness §11
**Tension:** Build Readiness §4.3 says every operation output "must include" all 11 fields; Harness §11's `OperationResult` interface marks 8 of them optional (`failureClass?`, `output?`, `recordsWritten?`, `eventsEmitted?`, `idempotencyKey?`, `contractVersion?`, `operationContractVersion?`, `productBuild?`), requiring only `operationName`, `succeeded`, `correlationId`.
**Decision:** the generated `*.output.schema.json` `required` = `[operationName, succeeded, correlationId]` — Harness §11 (the interface the ProductDriver actually implements) outranks Build Readiness §4.3. The other 8 are permitted (in `properties`) but not required. Type: registry/schema decision. Surfaced by the sprint-002 review.

### B-Q-9 — idempotency_key minLength
**Tension:** Build Readiness §8.2 (CaptureMeasurement) specifies `idempotency_key` as `{type:string, minLength:1}`; §8.3–§8.6 and the standard envelope §4.2 specify plain `{type:string}`.
**Decision:** match each section verbatim — `minLength:1` only for CaptureMeasurement; plain `string` for all other operations. No added constraint where the docs are silent. Type: schema decision (verbatim faithfulness).

## Discovered during sprint 005 (backend skeleton review)

Adversarial review of the backend (workflow w4zjlovog) found the first durability claim was OVERSTATED and a latent transactional bug. All fixed:
- **Overstated durability (blocker):** the fresh-instance re-eval reused the run's cached stepResults/checkpoints, so ~60/156 assertions (all `operation_succeeded`, `bounded_drill_down`, the checkpoint) never touched disk. Fixed: the durability proof (`evaluateDurable`) now evaluates ONLY persisted-state assertions with empty caches (96/96), excluding operation-outcome assertions (behavior, not stored state), and reports the exclusion honestly.
- **Checkpoint un-durable → event replay:** the persisted records table stores only current state, so `run_001 @after_step_047 = close_blocked` was unrecoverable from disk. Fixed: `BackendProductDriver.rebuildCheckpointsFromEvents()` replays the append-only event log (TAD §12/§27/§26) to rebuild historical record state; the checkpoint is now genuinely served from disk (verified: `047 → close_blocked`).
- **No per-op rollback (Contract Spec §8):** the engine caught handler throws but left partial mutations, so a failed op could persist records with no creation event. Fixed: `executeOperation` snapshots (structuredClone) and rolls back records/events/aliases/seq on failure; proven by the fault-injection discrimination test (a failing `RecordApprovalDecision` leaves zero facts).

### B-Q-11 — backend outbox is writer-only; durability scope is persisted-state
**Notes (skeleton scope, not defects):**
- The events table is append-only (INSERT OR IGNORE, no UPDATE/DELETE) and writes one outbox row per event transactionally, but the DELIVERY leg (a consumer that marks `delivered` and drives idempotent projection workers, TAD §12 at-least-once) is DEFERRED — `loadFromDisk` rebuilds directly from records+events. Claims downgraded accordingly in `backend.ts`.
- Durability is scoped to persisted STATE (records, events, replayed history). `operation_succeeded` and `bounded_drill_down_filtered` are operation OUTCOMES / transient results, not persisted facts — proven by the run (behavior), explicitly excluded from the durability proof. `BoundedDrillDown` input (`accessPolicies`) is a runtime World input, not persisted; a fresh instance does not re-execute it.
- The backend upserts the full record set per op (skeleton simplification, correct but not delta-optimized); a real backend tracks a dirty set.

### B-Q-13 — idempotency is in-instance memo, not write-boundary — RESOLVED (sprint 013)
First-slice idempotency WAS the `required_idempotency_key` in-instance memo only (Contract Spec §6 "return same result"): re-executing with the same key returns the prior result without re-running the handler — but NOT persistence-layer/cross-instance idempotency for `transactional_unique_constraint` ops, which would duplicate on a cold replay. **Resolved (sprint 013 hardening):** a `transactional_unique_constraint` op (CreateInventoryItem, CreateGrammarGap) now dedups by idempotency_key at the WRITE boundary — `World.txIdempotencyKeys` is a persisted seen-keys set; a second write with a seen key returns `idempotency_conflict` with zero facts, and the backend persists+reconstructs the set in `world_config` so the constraint SURVIVES a cold reload (proven by the 7th backend durability proof + `tests/hardening/write-boundary-idempotency.test.ts`). The two idempotency classes are now distinct and both enforced: `required_idempotency_key` -> in-instance memo (same result); `transactional_unique_constraint` -> persisted unique constraint (conflict). Both keys are OP-SCOPED (`${op}:${key}`) so two different ops sharing a key string do not collide, and neither records a key on a FAILED op (a transient failure does not poison the key). *Scaling caveat (deferred):* the backend serializes the whole `txIdempotencyKeys` set into the single `world_config` row on every persist (O(n) per op) with no eviction — fine at first-slice key volumes; a dedicated append-only `idempotency` table is the scaling fix for a later sprint.

## Discovered during sprint 008 (build-check-blocker family: VF-004/005/006)

Building the wrong/quarantined/missing-child scenarios surfaced two unexercised-path gaps (the VF-003A dynamic): `QuarantineInventory` was registered but had no handler (implemented per the state machine: `received -> quarantined`, emits `INVENTORY_QUARANTINED`), and the build check collapsed all three child-inventory failure modes into one `missing_bom_inventory` label. An adversarial review (workflow w5dmishnx, 3 critics, 9 confirmed) then found the first-cut blocker logic buggy; all fixed:
- **wrong_part search was world-global (major×3):** it flagged any usable non-target item not in a required set, so a genuinely MISSING child was mislabeled `wrong_part` whenever any stray item existed, multi-BOM-line runs cross-attributed one stray to every missing line, and `.find()` picked the first stray in insertion order rather than the wrong-revision of the specific part. Fixed: the search is now scoped by part IDENTITY (`part_number` + `revision`, loaded into `World.partRevisions` from `world.part_revisions`) — a wrong child is the same `part_number` in a different `revision`, judged per BOM line. Regression-tested (`tests/build-check` [3][4]).
- **schema gate was cosmetic (major):** `generate.ts` unions all `scenarios/*/references.yaml` but `validate-schemas.ts` validated only VF-003's set, so the new blocked-path schemas were generated but never validated. Fixed: `validate-schemas.ts` now mirrors the union (62 event schemas validated, was ~55).
- **durability proof was VF-003-only (minor):** `run-backend.ts` now also proves the BLOCKED path survives a reload — a fresh-from-disk instance re-passes VF-006 with `run_001=blocked`, `build_check_001=blocked`, and the missing-inventory blocker persisted.
- **evaluateDurable omitted operation_failed (minor):** the NON_DURABLE set excluded `operation_succeeded` but not `operation_failed`, so pointing the durability recipe at VF-005 spuriously failed. Added `operation_failed` (an operation outcome, not persisted state).

### B-Q-14 — build check names DISTINCT child-inventory blockers
The build check must NAME its blockers (Product Spec §212 "build checks name blockers and explain version selection"), and the first slice distinguishes three child-inventory failure modes the Harness §22 catalog names as separate scenarios: VF-006 missing, VF-005 quarantined, VF-004 wrong. Collapsing them into one label destroys information the Research Dossier says the system exists to preserve (distinct typed states, "preserve conflict instead of overwriting it"). **Decision:** `RunBuildCheck` emits, per install_required BOM line, exactly one of `missing_bom_inventory:<part>` (no unit of that part_number in the world), `quarantined_inventory:<part>` (the right part+revision exists but is on quality hold), or `wrong_part:<found>_expected:<part>` (a usable unit of the same part_number in a different revision). Part identity comes from `world.part_revisions`. The exact blocker strings are an executor-chosen encoding of the doc-specified behavior (block + name blocker), not invented product behavior — recorded here so the encoding is defendable. Type: registry/executor decision.

### B-Q-15 — CreateRun carries no build-check precondition (blocked run is created, then blocked)
Build Readiness §7.3 lists `BuildCheckResult.status == passed` as a `CreateRun` precondition, but the higher-authority Contract Spec v0.4.1 CreateRun refinement carries NO such precondition and its Run state machine explicitly defines `planned -> blocked via ApplyBuildCheckResultToRun emits RUN_BLOCKED` — a transition unreachable if CreateRun required `passed` (Build Readiness is internally self-contradictory on this point). **Decision:** resolve by authority order (Contract Spec > Build Readiness): a run may be created in `planned` on a blocked build check and then driven `planned -> blocked` by ApplyBuildCheckResultToRun. VF-004/005/006 exercise exactly this path; the engine invents no behavior and weakens no assertion. Type: cross-doc conflict resolved by authority order. (Surfaced by the sprint-008 review as an unrecorded decision — the behavior was already correct; this entry records it.)

### B-Q-16 — runtime emit() vocabulary enforcement — RESOLVED (sprint 013); payload-shape schemas still baseline
The event-TYPE + PRODUCER half of SDD technique #2 (poka-yoke at the speaker's mouth) is now enforced at RUNTIME, not only statically. **Resolved (sprint 013 hardening):** `World.emit(type, producer, payload)` validates against the `eventProducers` map (built from `events.yaml`) — an unregistered event type or a producer not registered for that event throws `emit_vocabulary_violation`, which `executeOperation` catches + rolls back, failing the operation. All 18 scenarios pass unchanged (the handlers were already registry-consistent), and `tests/hardening/emit-pokayoke.test.ts` proves the teeth (a bad pair throws; the correct pair passes). A future handler that emits a mis-attributed/unregistered tag now fails immediately rather than surviving as a stray event. **Still open (narrower):** the PAYLOAD-shape half — generated event payload schemas are the baseline `{type: object}` where the docs do not specify a payload shape, and emit() does not validate the payload against the schema. Payload correctness (e.g. the `BUILD_BLOCKER_CREATED.blocker` string) remains pinned by scenario assertions + discrimination tests, not an independent schema. Runtime payload-schema validation is deferred (most schemas are permissive by design; on the drift watchlist).

### B-Q-17 — EffectivityResolution flat selected fields
`ResolveEffectivity` stores `selected_procedure_version` / `selected_manufacturing_structure_version` as flat scalar fields in addition to the nested `selected: {ProcedureVersion, ManufacturingStructureVersion}`. **Decision:** Contract Spec §17 says the resolution carries the "selected target records"; the flat mirror is a representation choice (not invented behavior) that makes the selection assertable at the flat level the harness's `record_field_equals` supports (it does not read nested paths), and is what `CreateRun` reads to snapshot the effectivity context (B-Q-15/§17). Type: representation decision.

### B-Q-18 — no-match dominates ambiguity in ResolveEffectivity
When resolving across the required target types, one type may have NO matching rule ("fails resolution") while another has equal-priority matches ("creates ambiguity"). **Decision:** a missing required rule is a hard fail (`precondition_failed`) and DOMINATES an ambiguity elsewhere — you cannot resolve at all if a required target type has zero candidates. Decided after the full loop (deterministic regardless of target-type order; previously an order-dependent mid-loop throw could discard a collected ambiguity). Contract Spec §17 lists both outcomes but not their precedence when co-occurring; resolved here. Type: executor decision.

### B-Q-19 — build-check effectivity blocker strings
`RunBuildCheck` names two effectivity blockers as `BUILD_BLOCKER_CREATED` payloads: `effectivity_ambiguous` (the resolution is ambiguous) and `effectivity_not_resolved` (no resolution / not resolved for another reason). Type: registry/executor decision.

## Discovered during sprint 010 (access-filtered serial history + missing report definition: VF-009/010) — first-slice bench COMPLETE

### B-Q-20 — serial-history controlled/summary-safe filter predicate
Access-filtered serial history (Contract Spec §14.2/§19: SerialHistory reads full | summary | denied by reader) requires deciding WHICH entry detail is "controlled" (stripped under summary) vs summary-safe (kept). **Decision:** machine-evidence entries (`event_type` starting `MACHINE_EVIDENCE_`) carry controlled detail under the token `controlled_machine_evidence_payload`; under a policy whose `hidden` list contains that token the detail is stripped (`controlled_detail: null`) while the entry's `event_type` (the review STATUS) is LEFT visible. Grounded in Build Readiness §11.1 (customer_summary_access CAN see machine-evidence review status, CANNOT see raw/controlled payload) + §11.2 field split + the VF-003 policy hidden list (`controlled_machine_evidence_payload / raw_machine_payload / internal_quality_notes`). The token + the MACHINE_EVIDENCE_ predicate are the executor's encoding (Build Readiness is lowest authority and no entry field existed to hide), pinned by VF-009's `access_full`/`access_summary` assertions + the serial-history-access discrimination test. Scope: static full-vs-summary; temporal access-policy-change (Harness §17) and EvaluateAccess-driven denied+audit are deferred elaborations. Type: registry/executor decision.

### B-Q-21 — report-definition availability representation
The run-close rule `report_definition_available` (run-close-rules.yaml) requires representing whether a RunCloseReport DEFINITION is present vs missing for a run. `ReportDefinition` is a registered record (records.yaml) but has NO creating operation, and none may be invented. **Decision:** availability is a World condition — `World.reportDefinitionAvailable`, seeded from `scenario.world.report_definition_available` and DEFAULTING TRUE (available) — mirroring how access policies are seeded. ## Built during Phase B (§18 evidence-invalidation auto-cascades)

### B-Q-29 — RESOLVED (Phase B): the two §18 cascade obligations we had deferred
Contract Spec §18 lists six effects when accepted evidence is invalidated. VF-003D shipped four (don't mutate history; emit the superseding event; mark dependent reports affected; require report regeneration). Phase B builds the remaining two, extending `InvalidateAcceptedEvidence`:

- **"create run close observation if run still open"** — the cascade creates a `RunCloseObservation` (state `created`) and emits `RUN_CLOSE_OBSERVATION_CREATED` when the affected run is NOT terminal. **Encoding:** "still open" = `run.state ∉ {closed, cancelled}` (a run in `close_check`/`close_blocked` is still open — a fresh observation there correctly informs the in-progress close). Idempotent: one observation per invalidated evidence.
- **"create quality issue or nonconformance if physical product may be affected"** — the cascade opens a quality `Issue` (state `open`) and emits `ISSUE_OPENED`. **Encoding (the underspecified part):** "physical product MAY be affected" is not precisely defined by §18, so it is read FAIL-SAFE per §18's own default first-version rule ("quality review is required if artifact acceptability depended on the evidence"): the invalidated evidence was *accepted*, so an artifact's acceptability depended on it → always open a review Issue. Chose `Issue` (a review) over `Nonconformance` (an asserted non-conformity) as proportionate to "may". Prefer a false review over a missed one. Idempotent: one issue per invalidated evidence. Do NOT invent a physical-product-detection heuristic (none is in the world model) and do NOT auto-open a Nonconformance (over-asserts).

`InvalidateAcceptedEvidence` was registered as an additional producer of the already-registered `RUN_CLOSE_OBSERVATION_CREATED` (was: RunCloseCheck only) and `ISSUE_OPENED` (was: OpenIssue only) — a multi-producer pattern with precedent (NormalizeMachineEvidence + CreateGrammarGap both produce GRAMMAR_GAP_CREATED). No new events/records/ops invented — the vocabulary already had all four concepts. Pinned by `tests/reconciliation/evidence-invalidation-cascade.test.ts` (both obligations, run-open vs run-closed discrimination, fail-safe, idempotency, evidence linkage, fail-closed on unresolvable run), scenario VF-003F (open-run cascade on both drivers, in the whole-bench diff-to-zero), VF-003D (the Issue on the closed-run path), and a coupling mutation that turns VF-003F red if the cascade is suppressed. Type: executor encoding of an underspecified §18 rule (fail-safe), recorded here.

## Built during Phase A (outbox delivery leg)

### B-Q-30 — RESOLVED (Phase A): the outbox delivery leg (TAD §12)
The backend wrote outbox rows transactionally but nothing consumed them — the at-least-once eventing story was aspirational. Phase A builds `deliverOutbox()` (backend-only plumbing, below the operation layer, so NO registry change): it reads undelivered outbox rows in seq order, drives an idempotent projection handler (`delivery_projection` keyed by `event_seq`; a materialized `projection_counts` view incremented only on first apply), and marks each row delivered. Proven by a durability proof in `run-backend.ts` (first delivery applies every event once; a simulated crash loses delivered-marks; redelivery re-applies nothing with no double count; survives a reload) — gated into the backend exit and red-capability spot-checked (a non-idempotent bump fails it).

**Adversarial review hardening (the skeptic pass turned three over-claims into real guarantees):**
- **At-least-once was actually exactly-once.** Apply + mark were in ONE transaction, so the "crash between apply and mark" state was unreachable by real code — the idempotency defended a path only the test poke could reach. Fixed: apply and mark are now **two separate transactions**, so a crash after the apply-commit and before the mark-commit is a reachable durable state that forces a genuine redelivery. The split is what *makes* delivery at-least-once and *necessitates* the idempotent handler.
- **Ordering was verified by nothing** (the counter projection is order-insensitive; dropping `ORDER BY` still passed). Fixed: `deliverOutbox` returns the delivery `order`, and the proof scrambles outbox row-order (`__test_reverseOutboxRowOrder`) then asserts delivery still ascends by seq — falsifiable (dropping `ORDER BY` fails it, spot-checked).
- **Mark-without-apply on an orphan row.** An outbox row with no matching event was marked delivered without projecting. Fixed: an orphan is counted (`orphaned`) and **never marked delivered** (fail-safe). Plus `outbox.event_seq` is now `UNIQUE` (enqueue is `INSERT OR IGNORE`) so one-row-per-event is structural.
- Honest labelling: the "crash"/"reload" in the proof are in-process simulations (a reset of the delivered flag; a fresh handle on the same file), not a real process kill / fsync-recovery test — the comments say so.

**Deferred (genuinely out of scope, not built):** retries-with-backoff and dead-letter-after-retry-limit — TAD §12 lists them but specifies neither a backoff schedule nor a retry-limit magnitude, so a concrete value would be invented (same reasoning as the drill-down cap, B-Q-25). Revisit when the contract names the magnitudes. The richer domain projection types (as-built, serial history, etc.) remain computed-on-read as before; `delivery_projection`/`projection_counts` is the minimal materialized projection that exercises the delivery contract.

## Built 2026-07-30 — the two unevaluated required-work close rules (found by probe)

*A probe drove VF-001 on the real driver with a step's measurement dropped, and with the required child's installation dropped. In both cases the step completed, the run reached `closed`, `RUN_CLOSED` fired, the close check reported ZERO blockers, and the close report carried an empty `measurement_summary` / `installed_inventory`. `required_measurements_present` and `required_installations_present` are registered rules (Contract Spec §16) that nothing evaluated, and the `CompleteRunStep` precondition that Build Readiness §7 states was never implemented. A positive control (dropping a step COMPLETION instead) proved the harness could produce a refusal, so the permissiveness was the product's. Both gates are now built; the three encodings each forced a decision, recorded below.*

### B-Q-34 — RunStep carries which ProcedureStep it instantiates (positional pairing)
Build Readiness §CreateRun writes "**RunStep records from ProcedureVersion steps**", but the handler created them from the bare `run_step_aliases` list with only `{run}` — dropping the provenance. Nothing downstream could ask "what did this step require", which is exactly what the precondition and both close rules need. **Decision:** `CreateRun` now records `procedure_step` on each RunStep, pairing the ORDERED `run_step_aliases` input against the snapshot procedure version's steps sorted by `ordinal` — the Nth run step instantiates the Nth procedure step. The operation input carries no explicit mapping, so positional pairing is the encoding the input shape forces; it is faithful to "from ProcedureVersion steps" and is recorded here rather than left implicit. **Revisit if** an operation ever creates run steps out of procedure order, at which point the input needs an explicit mapping. Type: executor encoding.

### B-Q-35 — a SKIPPED step is still held to its step requirements (fail-safe)
`CompleteRunSteps` accepts steps that are `complete` **or skipped**, so a skipped step reaches the close gate — the path the `CompleteRunStep` precondition structurally cannot cover, and the reason the close rules are not redundant with it. §16 does not say whether skipping WAIVES a step's required measurement/installation. **Decision:** it does not — the close rule flags a skipped step whose required work never happened. Fail-safe, per the same reasoning as B-Q-29: a close report certifying a build whose required characteristic was never inspected, with nothing recording why, is precisely the false certainty this system exists to refuse; prefer a false block over a missed escape. **Revisit when** the contract names a legitimate skip-with-waiver path (see B-Q-36 — the two are the same missing concept seen from different sides). No scenario is affected today: `SkipRunStep` is registered but unimplemented. Type: executor encoding of an underspecified §16 rule.

### B-Q-36 — the "waived by approved redline" half of the CompleteRunStep precondition is NOT built
Build Readiness §7 states the precondition in full as "required measurements/installations for step are satisfied **or explicitly waived by approved redline**". The waiver half is deliberately not implemented: **no waiver is representable anywhere in the registries** — there is no `Waiver` record, no waiver field on `Redline`, and no waiver event — and the research dossier §300 is explicit that a deviation, waiver, NCR, MRB decision and redline "are not the same object", so reading an approved redline as a blanket waiver would collapse two distinct concepts AND invent the vocabulary to do it. **Decision:** the gate is unconditional; nothing is waived. This is the fail-closed direction (an unwaivable requirement blocks; a wrongly-waived one ships). **Revisit when** the contract introduces a waiver object with its own authority rules — that is a real gap in the vocabulary, not merely an unbuilt handler. ## Built 2026-07-31 — the receiving evidence boundary

*An outside registry pack (`receiving-evidence-registry-pack-v0.1`) proposed a Receiving module. Taken as input and mapped onto this project's existing vocabulary rather than adopted: its SupplierDocument is our Certificate, its verification record is our Verification, its inspection is a check shaped like RunCloseCheck, its quarantine is a blocker plus the existing inventory state, its corrective action is our Issue. ### B-Q-37 — receiving decides, inventory transitions
The pack's rule that Receiving must never write `InventoryItem` matches this project's module discipline, and we already have the shape for it: `RunBuildCheck` produces a result and `ApplyBuildCheckResultToRun` walks the Run transition. **Decision:** `RunReceivingCheck` writes only its own `ReceivingCheck`, and `ApplyReceivingCheckResultToInventory` — owned by Inventory — walks `received -> available` or `received -> quarantined`. Those two transitions gained the operation as a second `via` rather than getting duplicate rows, which the state machine already supports. The gate applies to goods that arrived on a shipment line; inventory with no line never crossed the boundary, and that is a positive fact about the item rather than the absence of a check. Type: registry decision.

### B-Q-38 — an unspecified consignment requires a certificate of conformance
`ShipmentLine.required_documents` says which documents a consignment must carry. **Decision:** when the caller does not specify, the line requires `certificate_of_conformance` alone — the one document every consignment carries. Requiring more by default would refuse legitimate goods; requiring nothing would make the boundary decorative. Anything beyond the default is scenario data, not an executor guess. **Revisit when** a supplier or part-family policy can express the requirement, at which point the default should come from that policy rather than from the handler. Type: executor encoding.

### B-Q-39 — expiry and scope are properties of the document TYPE, and absent is not expired
Reusing `Certificate`/`VerifyCertificate` for supplier paperwork had two faults, both found by pressure-testing the mapping before writing code. `VerifyCertificate` treats a missing expiry as invalid, which is right for a calibration certificate and wrong for a material test report or first article report — neither expires, so a blanket check would have refused valid paperwork. And it matches strictly on `serial_or_lot`, while a first article report covers a part revision and could never have been found. **Decision:** each registered receiving rule carries `expires` (whether the type has an expiry at all) and `scope` (`lot_or_serial` or `part_revision`). The scope idea is taken from the pack, which was better than us here. **And a third fault, found later by the mutation battery:** absent and expired had collapsed into a single blocker id, so suppressing the absent-document branch left VF-025 green because the expiry branch caught it as a side effect — the state-blurring VF-004/005/006 forbid. They are now distinct registered ids (`certificate_of_conformance_present` / `certificate_of_conformance_expired`). Type: executor encoding + registry decision.

### B-Q-40 — a quarantined target names its quarantine, like a quarantined child
**Tension:** `RunBuildCheck` names a quarantined CHILD precisely (`quarantined_inventory:<part>`), with a comment citing B-Q-14 that missing / quarantined / wrong-part are distinct facts which must not collapse to one label. Twenty lines earlier, a quarantined TARGET reported the generic `target_inventory_not_available` — the same collapse the neighbouring code exists to prevent, blurring "on quality hold" with "absent or not yet received".
**Why it surfaced now:** the asymmetry was latent because nothing routinely quarantined a target item. The receiving boundary does exactly that as its ordinary behaviour, so the first real use of receiving lands on the one path that discarded the reason. **Decision:** a quarantined target emits `quarantined_inventory:<alias>`; `target_inventory_not_available` is kept for genuinely absent or not-yet-received stock. No scenario asserted the old string, so the change is additive in effect. Type: pre-existing defect, corrected.

### B-Q-41 — a supplier document may itself be export-controlled
ITAR 22 CFR 120.33 defines technical data as information necessary for design, development, production, manufacture, assembly, repair or testing of a defense article, in forms including drawings, diagrams, tables and engineering specifications. A dimensional report or first article report records measured characteristics against drawing dimensions and falls squarely in that definition; a certificate of conformance, which attests conformity rather than describing how the article was made, generally does not. **Decision:** export control is declared PER DOCUMENT on the `Certificate` record (`export_control`), not per document type, and is read by the existing `EvaluateAccess` nationality gate built for persona gap 5 — no second access mechanism. A document with no `export_control` is uncontrolled, which is that operation's existing definition. **Deliberately NOT built:** a token hiding supplier documents from a customer summary view. Supplier quality flow-downs (Collins, Howmet, L3Harris) reserve customer and regulatory right of access to records at every level of the supply chain, so hiding certificates from the customer who bought the part would model the wrong thing. Type: executor encoding + recorded non-goal.

Type: scope note.

### B-Q-45 — run_context_snapshot_exists: structurally satisfied
`CreateRun` always writes a `RunContextSnapshot`, and a Run cannot be created any other way, so a run reaching close without one is unreachable through registered operations. **Decision:** no close-time check added, for the same reason as B-Q-44. Type: scope note.

## Built 2026-07-31 — the outbound certificate of conformance

### B-Q-46 — the certificate is a governed report, not a new subsystem
A part does not leave alone: it ships with a certificate of conformance, and AS9163/EN 9163 fixes that certificate's minimum content — certificate number, date, supplier and customer, purchase order, item/quantity/description/revision, traceability, a conformity statement and an authorized signer — and requires a REVISED certificate to carry a new distinguishable number, a revision reason and a new release date. **Decision:** register it as a second governed report rather than a new module. The report machinery already has the exact shape: a definition version, a bound access scope, `filtering_mode: controlled_export`, and supersession under a named trigger, all built for VF-012 — AS9163's revision rule IS report supersession. The RunCloseReport is an internal record of how a run went; the certificate is an outbound attestation to a customer, so they are two reports, not one. Type: registry decision.

### B-Q-47 — no certificate, no shipment; and a certificate needs an identified signer
The inbound law is that goods arriving without paperwork are not production eligible. **Decision:** the outbound mirror is that goods leaving without a certificate are not shippable. `ShipInventory` fails closed with `no_certificate_of_conformance` unless a generated certificate actually LISTS the serial — not merely exists, since a certificate covering other goods attests nothing about this one. `GenerateCertificateOfConformance` refuses an unidentified signer and a certificate covering zero serials, matching the approval discipline (persona gap 2): who signed, when, and what the signature attests. **Not built:** a controlled exception path for shipping under deviation. It would need an authority model and a deviation record the contract does not define, and an ungoverned override would hollow out the gate — the receiving pack made the same call for its own release path. Type: executor encoding + recorded non-goal.

## Built 2026-07-31 — attachments: the file behind the record

### B-Q-48 — the record holds a reference, and an attachment is evidence until accepted
The Attachment Module was fully specified — eight operations, a seven-state lifecycle, object storage, a harness mock — and had no handler, so a `Certificate` asserted that a certificate existed while nothing held the document.
**Decisions:** (a) TAD §11 puts the bytes in object storage and metadata plus a reference in the database, which is why the terminal operation is `DeleteAttachmentReference` — it clears the reference and keeps the record, its state and its history, matching the no-deletions discipline. (b) An attachment follows the machine-evidence doctrine: uploading proves nothing, it must be LINKED to the record it supports and then accepted before it counts, and the reject and review paths are reachable alternatives. Acceptance is a signature — who accepted, when, and what it attests — and refuses an unidentified actor, matching persona gap 2. (c) `GetAttachment` fails CLOSED: a restricted attachment, or one whose reference was deleted, returns metadata and an explicit `withheld_reason` rather than a storage reference. Handing back the reference and trusting the caller not to fetch it would be a fail-open on controlled technical data.
**Not built:** a receiving rule requiring that a required supplier document carry an attachment. It is the natural completion — a certificate record with no document behind it is a claim — but making it blocking would refuse every consignment in the existing scenarios, and the contract does not say a document record is insufficient without its file. **Revisit when** the receiving rules can express per-supplier or per-part evidence depth. Type: unimplemented module, now built + recorded non-goal.

### B-Q-49 — three fail-open holes in the same day's work, found by pressure test
Probing the outbound and receiving gates with inputs no scenario supplies found three, all the shape practice #19 predicts a fast batch of guards will take.
**(a) A certificate of conformance could be issued for quarantined goods** — attesting conformity for material on quality hold, the plainest false certainty this system exists to refuse. Fixed with an ALLOW-list, not a deny-list: only `available`, `reserved`, `kitted` or `installed` goods can be certified; everything else raises `uncertifiable_inventory_state`.
**(b) A certificate for one part released a different part sharing a serial number.** `ShipInventory` matched the serial string alone, but a serial is unique within a part, not across the world. This is the identical cross-part collision the affected-population check closed in sprint 019, reintroduced in new code. Now matched on serial AND part revision.
**(c) A shipment line could reference an inventory item that does not exist**, so the line marked nothing as supplier-received and the goods it claimed to cover never entered the boundary at all. The item is now resolved at line creation.
All three locked by `tests/shipping/outbound-certificate.test.ts`, including the not-blanket case for (a) and the still-ships case for (b). Type: defects, corrected.

## Built 2026-07-31 — closing the loose ends the receiving/outbound work left

### B-Q-50 — quarantined goods leave quarantine only through their own gate
The receiving boundary was a trap: VF-025 quarantined a valve body for a missing certificate and `ReleaseFromQuarantine` had no handler, so nothing could let it out when the supplier sent one. **Decision:** built, but release is not an override. If the item arrived on a shipment line — a positive fact, not the absence of a check — it may leave quarantine only when a `ReceivingCheck` for that line currently reads `passed`; goods held for other reasons are outside the receiving boundary and release on the quality path. Who released it and why are recorded. VF-030 proves both halves: release refused on the strength of the paperwork alone, then allowed once the gate is re-run and passes. Type: dead-end corrected.

### B-Q-51 — the close report now carries the attachments it claimed
`reports.yaml` lists `Attachment` among RunCloseReport's source records and the assembler referenced none. Harmless while attachments did not exist; a registry claim the code did not honour once they did. **Decision:** accepted attachments are carried in `source_traceability.attachment_ids`. Accepted only — an unaccepted attachment is not evidence and must not be claimed as a source. Contract Spec §15 names Attachment a source RECORD, not a required section, so no new section was invented. Type: registry/code divergence corrected.

### B-Q-52 — the Issue lifecycle, so a quality issue can be worked
Issues could be created — the §18 evidence cascade opens one, a receiving failure maps to one — and never worked, so they accumulated as dead-end records. **Decision:** the registered lifecycle is built (open → triaged → resolved → closed, cancel from open or triaged), each step recording who did it. `ResolveIssue` refuses a resolution with nothing stated and `CancelIssue` refuses a cancellation with no reason, because an issue closed with no record of what was judged is worse than an open one. Triage carries an assessment and whether it becomes a nonconformance: an Issue is broad, a Nonconformance is specific, and the dossier is explicit they are not the same object. Type: unimplemented lifecycle, now built.

**Also corrected:** `document_matches_part_revision` was registered with no `cert_type`, so `required_documents` could never select it — dead vocabulary. It is now enforced on every document match: a lot-or-serial scoped document must also name the part revision it is offered against, and one matching the serial but naming a different part raises the rule. This is the inbound twin of B-Q-49(b), the same cross-part collision caught outbound. And the certificate allow-list was widened to include `shipped`, because AS9163 revisions exist precisely to correct a certificate after the goods have gone.

## Discovered by the valve-body demo pack (writing the domain out as plain data)

*Source: `demo-packs/valve-body-assembly-v0.1/`. Writing VF-003's valve body out as plain files — part, BOM, procedure, tool, serials, torque check, quality path, customer view, report — surfaced three things the vocabulary has no word for. The pack invents nothing (`check.mjs` proves every name it uses is registered); the gaps are recorded here and left unbuilt rather than papered over. None are blocking: VF-003 and the whole bench run without them, because the system carries the same information on other records.*

### B-Q-31 — no standalone Part record
A part exists in the registries only as a `(part_number, revision)` pair carried on `ManufacturingStructureVersion`, `InventoryItem`, and `EffectivityRule`. There is no `Part` record, so there is nowhere to hang a drawing reference, a material spec, or the revision authority — the things a real part master carries. **Not built:** creating a `Part` record would be new product vocabulary the doc stack does not define, and it ripples into every record that currently carries the pair (identity, ownership, and the effectivity join would all need decisions). **Revisit when** a scenario needs part-level attributes that cannot live on the structure version — the first candidate is drawing/material provenance on the run-close report. Type: recorded gap, unbuilt.

### B-Q-32 — the inspection requirement has no record of its own
The torque band (10–12 Nm, nominal 11) lives in two places — a `ProcedureStep`'s data-collection field and the scenario's world data — and nowhere as a single thing a `Measurement` points to. `CaptureMeasurement` evaluates against limits it is handed, so the requirement itself is not a governed, versioned object: two runs can be measured against different bands with nothing recording that the requirement changed. **Not built:** an `InspectionRequirement` record with its own effectivity would be new vocabulary, and the Contract Spec does not define one. **Revisit when** a scenario needs to prove which requirement version a measurement was judged against (the natural pair for the existing effectivity machinery). Type: recorded gap, unbuilt.

### B-Q-33 — no operation for scanning a serial
Serials arrive only as inputs to other operations (`StartRunWithInventory`, `InstallInventory`, `CaptureMeasurement`). There is no operation meaning "this physical part is in front of me now" — so a floor scanner has no step to call, and the record cannot distinguish an asserted serial from a scanned one. **Not built:** a `ScanSerial` operation (and whatever evidence it would carry) is not in the contract stack; inventing one would also imply an identity-confidence dimension the world model does not have. **Revisit when** the floor-facing surface is specified — this is the first operation a UI or scanner integration will need. Type: recorded gap, unbuilt.
