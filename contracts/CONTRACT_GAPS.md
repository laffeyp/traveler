# Contract gaps and registry decisions — first slice (contracts-0.4.1)

*Typed log of every place the contract stack underspecified or conflicted, and how the registry extraction resolved it. Per the executor rule: a resolution is either a recorded registry decision (faithful to the higher-authority document) or a typed `ContractGap` for the Architect. Nothing here is invented behavior. Authority order: Contract Spec v0.4.1 > Harness v0.1.2 > VF-003 v0.1.1 > Build Readiness v0.2 > earlier docs.*

## Resolved as registry decisions (ratified for sprint 001)

### B-Q-1 — QualityContainmentAction state machine
**Tension:** Build Readiness §7.5 gives `QualityContainmentAction` a `required → active` lifecycle; Contract Spec §8/§10 first-slice state-machine lists omit it, while the handler-wrapper rule forbids transitions not in a registered machine.
**Decision:** registered a `QualityContainmentAction` state machine in `state-machines.yaml` (`null → required` via `StartQualityContainment`; `required → active` via `ActivateQualityContainment`). Additive, faithful to both docs. Type: registry decision (additive alignment item for the TAD amendment ledger).

### B-Q-2 — StartQualityContainment / ActivateQualityContainment from disposition_pending
**Tension:** Contract Spec §10.3 authorizes `StartQualityContainment` only as `Nonconformance: open → containment_required`. VF-003 calls `DefineAffectedPopulation` first (NC → `disposition_pending`) then `StartQualityContainment` then `ActivateQualityContainment`, and asserts NC == `disposition_pending` after step 028.
**Decision:** added explicit `disposition_pending → disposition_pending` self-loop transitions for both `StartQualityContainment` (emits `QUALITY_CONTAINMENT_REQUIRED`) and `ActivateQualityContainment` (emits `QUALITY_CONTAINMENT_STARTED`) in the Nonconformance machine. These emit the containment events without changing NC state, faithfully encoding Build Readiness §7.5's "when not already disposition_pending" conditional. The containment lifecycle itself is carried by the `QualityContainmentAction` machine (B-Q-1). Type: registry decision. *Highest-risk item — the handler must take the self-loop path, not force `open → containment_required`.*

### B-Q-3 — ReworkRun / Verification canonical names
**Tension:** Contract Spec §15 + TAD §5.8 use `ReworkRun` / `Verification`; Build Readiness §5.2/§7.5/§9.3 use `ReworkRecord` / `VerificationRecord`.
**Decision:** canonical = `ReworkRun`, `Verification` (higher authority wins). `records.yaml`, projections, and reports use the canonical names; Build Readiness's names are aliases, not carried forward. Type: registry decision.
**Alias map (for anyone reading Build Readiness §5.2/§9.3):** `ReworkRecord` -> `ReworkRun`; `VerificationRecord` -> `Verification`. `SerialHistory.source_records` and `RunCloseReport.source_records` use the canonical names and resolve cleanly against `records.yaml` (validator-confirmed: no dangling reference). Build Readiness §5.2/§9.3 should be corrected to the canonical names in a future amendment; the registry does not adopt the divergent spelling. Verified clean by the 6-critic adversarial pass (sprint 001); this was the single non-blocking finding and is resolved here.

### B-Q-4 — INVENTORY_IN_WIP cardinality
**Tension:** `StartRunWithInventory` moves both valve body and gasket to `in_wip`; VF-003 §10 lists `INVENTORY_IN_WIP` once.
**Decision:** `StartRunWithInventory` emits **one `INVENTORY_IN_WIP` per item moved** (two in VF-003). VF-003 §10's sequence is a non-exhaustive "highlights" list (its own header), so the Event Trace Tester asserts presence/order of highlighted events, not exact multiplicity. The InventoryItem state paths (valve_body ends `in_wip`, gasket passes through `in_wip`) are the binding assertions. Type: registry decision. Architect confirmed one-event-per-item.

### B-Q-5 — REDLINE_APPROVED cross-module producer
**Tension:** `RecordApprovalDecision` (Approval Module) drives `Redline: under_review → approved` and emits `REDLINE_APPROVED` (Redline Module); TAD §5.22 says events are emitted by the module owning the state change.
**Decision:** `events.yaml` registers `REDLINE_APPROVED` (and `REDLINE_REJECTED`) with `owning_module: redline` and `producer_operations: [RecordApprovalDecision]`. Producer ≠ owner is permitted and already occurs elsewhere in Contract Spec §13. The Redline machine lists `RecordApprovalDecision` as the `via` for the `under_review → approved`/`rejected` transitions. Type: registry decision.

### B-Q-6 — eleven registries
**Tension:** the abbreviated bootstrap summary listed nine registries.
**Decision:** added `observability-profiles.yaml` and `compatibility-profiles.yaml` (Contract Spec §3, §5). Every operation carries `observability_ref` + `compatibility_ref`. Type: inclusion, no behavior decision.

### B-Q-7 — BUILD_CHECK_FAILED vs BUILD_CHECK_BLOCKED (discovered during extraction)
**Tension:** TAD §5.12 names `BUILD_CHECK_FAILED` (+ `BUILD_BLOCKER_CREATED`); Build Readiness §7.3 says `RunBuildCheck` emits `BUILD_CHECK_PASSED or BUILD_CHECK_BLOCKED`. VF-003 only exercises `BUILD_CHECK_STARTED` + `BUILD_CHECK_PASSED`, so the failed/blocked path is non-VF-003.
**Decision:** canonical = `BUILD_CHECK_FAILED` + `BUILD_BLOCKER_CREATED` (TAD outranks Build Readiness). `BUILD_CHECK_BLOCKED` is not registered. Type: registry decision; flagged for Architect awareness.

## Scope decisions (registry boundary)

### Single source of truth for ownership
`modules.yaml` is the module **identity** registry; ownership of each record/operation/event is recorded on that record/operation/event (`owning_module`). This satisfies "exactly one owning module" by construction and avoids double-maintenance dangling. Faithful to TAD §5's intent.

### Events without a first-slice producer are deferred
The CI gate "no event without producer operation" means only events produced by a first-slice operation (§21.1) are registered. Deferred events with no first-slice producer (and thus excluded from `events.yaml` for now):
`INVENTORY_MOVED`, `INVENTORY_STATE_CHANGED` (no `MoveInventory` in first slice);
`AS_BUILT_PROJECTION_UPDATED`, `AS_BUILT_PROJECTION_REBUILT` (projection-worker producers, not first-slice);
`MRB_DECISION_RECORDED`, `CAPA_STUB_CREATED`, `FOD_INCIDENT_OPENED/CLOSED` (Quality ops not in §21.1);
`EVIDENCE_ACCEPTANCE_POLICY_CREATED`, `EFFECTIVITY_AMBIGUITY_RESOLVED`, `SUPPORT_ACCESS_*`, `SERVICE_ACCOUNT_*`,
all Reconciliation / Adapter Runtime / Virtual Factory Harness / Human Validation / GrammarGap-lifecycle events.
These are registered when their producer operations enter a later slice. Type: scope note, not a gap.

### Measurement is result-valued, not a state machine
Per Contract Spec §11, `Measurement.result ∈ {not_evaluated, pass, fail, warning}`; no Measurement state machine is registered. VF-003 §1.3's "required state machines" wording is superseded by §11. `scenario-assertions` target `Measurement.result`. Type: registry decision.

### RunStep creation is implicit
Per Contract Spec §0.2.7, `RunStep` is created under `CreateRun` with no own creation event; its machine declares `creation_transition: implicit_under_CreateRun` and has no `null ->` row. The four records mandated explicit creation transitions (Run, InventoryItem, MachineEvidenceRecord, Nonconformance, plus QualityContainmentAction) each have a `null ->` row (Contract Spec §0.1.4). Type: registry decision.

## Discovered during sprint 002 (schema-generation review)

### B-Q-8 — Operation output shape: Build Readiness §4.3 vs Harness §11
**Tension:** Build Readiness §4.3 says every operation output "must include" all 11 fields; Harness §11's `OperationResult` interface marks 8 of them optional (`failureClass?`, `output?`, `recordsWritten?`, `eventsEmitted?`, `idempotencyKey?`, `contractVersion?`, `operationContractVersion?`, `productBuild?`), requiring only `operationName`, `succeeded`, `correlationId`.
**Decision:** the generated `*.output.schema.json` `required` = `[operationName, succeeded, correlationId]` — Harness §11 (the interface the ProductDriver actually implements) outranks Build Readiness §4.3. The other 8 are permitted (in `properties`) but not required. Type: registry/schema decision. Surfaced by the sprint-002 review.

### B-Q-9 — idempotency_key minLength
**Tension:** Build Readiness §8.2 (CaptureMeasurement) specifies `idempotency_key` as `{type:string, minLength:1}`; §8.3–§8.6 and the standard envelope §4.2 specify plain `{type:string}`.
**Decision:** match each section verbatim — `minLength:1` only for CaptureMeasurement; plain `string` for all other operations. No added constraint where the docs are silent. Type: schema decision (verbatim faithfulness).

## Discovered during sprint 005 (backend skeleton review)

Adversarial review of the backend (workflow w4zjlovog) found the first durability claim was OVERSTATED and a latent transactional bug. All fixed:
- **Overstated durability (blocker):** the fresh-instance re-eval reused the run's cached stepResults/checkpoints, so ~60/156 assertions (all `operation_succeeded`, `bounded_drill_down`, the checkpoint) never touched disk. Fixed: the durability proof (`evaluateDurable`) now evaluates ONLY persisted-state assertions with empty caches (96/96), excluding operation-outcome assertions (behavior, not stored state), and reports the exclusion honestly.
- **Checkpoint un-durable → event replay:** the persisted records table stores only current state, so `run_001 @after_step_047 = close_blocked` was unrecoverable from disk. Fixed: `BackendProductDriver.rebuildCheckpointsFromEvents()` replays the append-only event log (TAD §12/§27/§26) to rebuild historical record state; the checkpoint is now genuinely served from disk (verified: `047 → close_blocked`).
- **No per-op rollback (Contract Spec §8):** the engine caught handler throws but left partial mutations, so a failed op could persist records with no creation event. Fixed: `executeOperation` snapshots (structuredClone) and rolls back records/events/aliases/seq on failure; proven by the fault-injection discrimination test (a failing `RecordApprovalDecision` leaves zero facts).

### B-Q-11 — backend outbox is writer-only; durability scope is persisted-state
**Notes (skeleton scope, not defects):**
- The events table is append-only (INSERT OR IGNORE, no UPDATE/DELETE) and writes one outbox row per event transactionally, but the DELIVERY leg (a consumer that marks `delivered` and drives idempotent projection workers, TAD §12 at-least-once) is DEFERRED — `loadFromDisk` rebuilds directly from records+events. Claims downgraded accordingly in `backend.ts`.
- Durability is scoped to persisted STATE (records, events, replayed history). `operation_succeeded` and `bounded_drill_down_filtered` are operation OUTCOMES / transient results, not persisted facts — proven by the run (behavior), explicitly excluded from the durability proof. `BoundedDrillDown` input (`accessPolicies`) is a runtime World input, not persisted; a fresh instance does not re-execute it.
- The backend upserts the full record set per op (skeleton simplification, correct but not delta-optimized); a real backend tracks a dirty set.

### B-Q-13 — idempotency is in-instance memo, not write-boundary — RESOLVED (sprint 013)
First-slice idempotency WAS the `required_idempotency_key` in-instance memo only (Contract Spec §6 "return same result"): re-executing with the same key returns the prior result without re-running the handler — but NOT persistence-layer/cross-instance idempotency for `transactional_unique_constraint` ops, which would duplicate on a cold replay. **Resolved (sprint 013 hardening):** a `transactional_unique_constraint` op (CreateInventoryItem, CreateGrammarGap) now dedups by idempotency_key at the WRITE boundary — `World.txIdempotencyKeys` is a persisted seen-keys set; a second write with a seen key returns `idempotency_conflict` with zero facts, and the backend persists+reconstructs the set in `world_config` so the constraint SURVIVES a cold reload (proven by the 7th backend durability proof + `tests/hardening/write-boundary-idempotency.test.ts`). The two idempotency classes are now distinct and both enforced: `required_idempotency_key` -> in-instance memo (same result); `transactional_unique_constraint` -> persisted unique constraint (conflict). Both keys are OP-SCOPED (`${op}:${key}`) so two different ops sharing a key string do not collide, and neither records a key on a FAILED op (a transient failure does not poison the key). *Scaling caveat (deferred):* the backend serializes the whole `txIdempotencyKeys` set into the single `world_config` row on every persist (O(n) per op) with no eviction — fine at first-slice key volumes; a dedicated append-only `idempotency` table is the scaling fix for a later sprint.

## Discovered during sprint 008 (build-check-blocker family: VF-004/005/006)

Building the wrong/quarantined/missing-child scenarios surfaced two unexercised-path gaps (the VF-003A dynamic): `QuarantineInventory` was registered but had no handler (implemented per the state machine: `received -> quarantined`, emits `INVENTORY_QUARANTINED`), and the build check collapsed all three child-inventory failure modes into one `missing_bom_inventory` label. An adversarial review (workflow w5dmishnx, 3 critics, 9 confirmed) then found the first-cut blocker logic buggy; all fixed:
- **wrong_part search was world-global (major×3):** it flagged any usable non-target item not in a required set, so a genuinely MISSING child was mislabeled `wrong_part` whenever any stray item existed, multi-BOM-line runs cross-attributed one stray to every missing line, and `.find()` picked the first stray in insertion order rather than the wrong-revision of the specific part. Fixed: the search is now scoped by part IDENTITY (`part_number` + `revision`, loaded into `World.partRevisions` from `world.part_revisions`) — a wrong child is the same `part_number` in a different `revision`, judged per BOM line. Regression-tested (`tests/build-check` [3][4]).
- **schema gate was cosmetic (major):** `generate.ts` unions all `scenarios/*/references.yaml` but `validate-schemas.ts` validated only VF-003's set, so the new blocked-path schemas were generated but never validated. Fixed: `validate-schemas.ts` now mirrors the union (62 event schemas validated, was ~55).
- **durability proof was VF-003-only (minor):** `run-backend.ts` now also proves the BLOCKED path survives a reload — a fresh-from-disk instance re-passes VF-006 with `run_001=blocked`, `build_check_001=blocked`, and the missing-inventory blocker persisted.
- **evaluateDurable omitted operation_failed (minor):** the NON_DURABLE set excluded `operation_succeeded` but not `operation_failed`, so pointing the durability recipe at VF-005 spuriously failed. Added `operation_failed` (an operation outcome, not persisted state).

### B-Q-14 — build check names DISTINCT child-inventory blockers
The build check must NAME its blockers (Product Spec §212 "build checks name blockers and explain version selection"), and the first slice distinguishes three child-inventory failure modes the Harness §22 catalog names as separate scenarios: VF-006 missing, VF-005 quarantined, VF-004 wrong. Collapsing them into one label destroys information the Research Dossier says the system exists to preserve (distinct typed states, "preserve conflict instead of overwriting it"). **Decision:** `RunBuildCheck` emits, per install_required BOM line, exactly one of `missing_bom_inventory:<part>` (no unit of that part_number in the world), `quarantined_inventory:<part>` (the right part+revision exists but is on quality hold), or `wrong_part:<found>_expected:<part>` (a usable unit of the same part_number in a different revision). Part identity comes from `world.part_revisions`. The exact blocker strings are an executor-chosen encoding of the doc-specified behavior (block + name blocker), not invented product behavior — recorded here so the encoding is defendable. Type: registry/executor decision.

### B-Q-15 — CreateRun carries no build-check precondition (blocked run is created, then blocked)
Build Readiness §7.3 lists `BuildCheckResult.status == passed` as a `CreateRun` precondition, but the higher-authority Contract Spec v0.4.1 CreateRun refinement carries NO such precondition and its Run state machine explicitly defines `planned -> blocked via ApplyBuildCheckResultToRun emits RUN_BLOCKED` — a transition unreachable if CreateRun required `passed` (Build Readiness is internally self-contradictory on this point). **Decision:** resolve by authority order (Contract Spec > Build Readiness): a run may be created in `planned` on a blocked build check and then driven `planned -> blocked` by ApplyBuildCheckResultToRun. VF-004/005/006 exercise exactly this path; the engine invents no behavior and weakens no assertion. Type: cross-doc conflict resolved by authority order. (Surfaced by the sprint-008 review as an unrecorded decision — the behavior was already correct; this entry records it.)

### B-Q-16 — runtime emit() vocabulary enforcement — RESOLVED (sprint 013); payload-shape schemas still baseline
The event-TYPE + PRODUCER half of SDD technique #2 (poka-yoke at the speaker's mouth) is now enforced at RUNTIME, not only statically. **Resolved (sprint 013 hardening):** `World.emit(type, producer, payload)` validates against the `eventProducers` map (built from `events.yaml`) — an unregistered event type or a producer not registered for that event throws `emit_vocabulary_violation`, which `executeOperation` catches + rolls back, failing the operation. All 18 scenarios pass unchanged (the handlers were already registry-consistent), and `tests/hardening/emit-pokayoke.test.ts` proves the teeth (a bad pair throws; the correct pair passes). A future handler that emits a mis-attributed/unregistered tag now fails immediately rather than surviving as a stray event. **Still open (narrower):** the PAYLOAD-shape half — generated event payload schemas are the baseline `{type: object}` where the docs do not specify a payload shape, and emit() does not validate the payload against the schema. Payload correctness (e.g. the `BUILD_BLOCKER_CREATED.blocker` string) remains pinned by scenario assertions + discrimination tests, not an independent schema. Runtime payload-schema validation is deferred (most schemas are permissive by design; on the drift watchlist).

### B-Q-17 — EffectivityResolution flat selected fields
`ResolveEffectivity` stores `selected_procedure_version` / `selected_manufacturing_structure_version` as flat scalar fields in addition to the nested `selected: {ProcedureVersion, ManufacturingStructureVersion}`. **Decision:** Contract Spec §17 says the resolution carries the "selected target records"; the flat mirror is a representation choice (not invented behavior) that makes the selection assertable at the flat level the harness's `record_field_equals` supports (it does not read nested paths), and is what `CreateRun` reads to snapshot the effectivity context (B-Q-15/§17). Type: representation decision.

### B-Q-18 — no-match dominates ambiguity in ResolveEffectivity
When resolving across the required target types, one type may have NO matching rule ("fails resolution") while another has equal-priority matches ("creates ambiguity"). **Decision:** a missing required rule is a hard fail (`precondition_failed`) and DOMINATES an ambiguity elsewhere — you cannot resolve at all if a required target type has zero candidates. Decided after the full loop (deterministic regardless of target-type order; previously an order-dependent mid-loop throw could discard a collected ambiguity). Contract Spec §17 lists both outcomes but not their precedence when co-occurring; resolved here. Type: executor decision.

### B-Q-19 — build-check effectivity blocker strings
`RunBuildCheck` names two effectivity blockers as `BUILD_BLOCKER_CREATED` payloads: `effectivity_ambiguous` (the resolution is ambiguous) and `effectivity_not_resolved` (no resolution / not resolved for another reason). Type: registry/executor decision.

## Discovered during sprint 010 (access-filtered serial history + missing report definition: VF-009/010) — first-slice bench COMPLETE

### B-Q-20 — serial-history controlled/summary-safe filter predicate
Access-filtered serial history (Contract Spec §14.2/§19: SerialHistory reads full | summary | denied by reader) requires deciding WHICH entry detail is "controlled" (stripped under summary) vs summary-safe (kept). **Decision:** machine-evidence entries (`event_type` starting `MACHINE_EVIDENCE_`) carry controlled detail under the token `controlled_machine_evidence_payload`; under a policy whose `hidden` list contains that token the detail is stripped (`controlled_detail: null`) while the entry's `event_type` (the review STATUS) is LEFT visible. Grounded in Build Readiness §11.1 (customer_summary_access CAN see machine-evidence review status, CANNOT see raw/controlled payload) + §11.2 field split + the VF-003 policy hidden list (`controlled_machine_evidence_payload / raw_machine_payload / internal_quality_notes`). The token + the MACHINE_EVIDENCE_ predicate are the executor's encoding (Build Readiness is lowest authority and no entry field existed to hide), pinned by VF-009's `access_full`/`access_summary` assertions + the serial-history-access discrimination test. Scope: static full-vs-summary; temporal access-policy-change (Harness §17) and EvaluateAccess-driven denied+audit are deferred elaborations. Type: registry/executor decision.

### B-Q-21 — report-definition availability representation
The run-close rule `report_definition_available` (run-close-rules.yaml) requires representing whether a RunCloseReport DEFINITION is present vs missing for a run. `ReportDefinition` is a registered record (records.yaml) but has NO creating operation, and none may be invented. **Decision:** availability is a World condition — `World.reportDefinitionAvailable`, seeded from `scenario.world.report_definition_available` and DEFAULTING TRUE (available) — mirroring how access policies are seeded. Default-available is the required polarity so a normal run (VF-003) closes unaffected; a scenario withholds the definition with `report_definition_available: false` (VF-010).
